# Knowledge Vault

Obsidianで読み書きする知識の正本。`intrahub-mastra`のAgentがこのVaultを生成・更新し、人間が確認と判断を担う。

このREADMEはVaultの構造と命名の規約を定める。エージェントが従う規則は`AGENTS.md`に要約してある。生成側の設計（Agent、Workflow、MCPの構成）は`intrahub-mastra/docs/codex-chat.md`にある。

実環境では`/srv/knowledge`として配置し、Mastraへは`/workspace`としてマウントする。

## 構成

```text
KnowledgeVault/
├── ai-workspace/               # 中間データ
├── second-brain/               # Obsidian Vault（資料由来の知識）
│   ├── 00-Inbox/               # 人手確認が必要なノート
│   ├── 10-Sources/             # 資料単位のノート
│   │   ├── Works/
│   │   ├── Papers/
│   │   └── Academic-Books/
│   ├── 20-Knowledge/           # 再利用する知識
│   │   ├── Concepts/
│   │   ├── Themes/
│   │   ├── People/
│   │   ├── Organizations/
│   │   └── Events/
│   ├── 30-Syntheses/           # 比較・年表・論考
│   ├── 40-Maps/                # MOC・索引
│   ├── 90-Meta/                # テンプレート、分類、検証レポート
│   └── Attachments/            # Vault固有の小規模な添付
└── tech-notes/                 # Obsidian Vault（開発由来の技術知識）
    ├── knowledge/              # 再利用可能な技術知識。カテゴリ別
    │   ├── concurrency/
    │   ├── storage/
    │   └── ...
    ├── decisions/              # 実プロジェクトでの選択記録（ADR）
    ├── MOC/                    # 分野ごとの入口。Dataviewクエリのみ
    ├── templates/
    └── attachments/
```

`second-brain`と`tech-notes`は目的も出典の形も異なるため、単一Vaultに統合しない。`second-brain`の出典は書誌情報とMediaVaultの抽出結果であり、`tech-notes`の出典はコミット、変更差分、実際に観測した挙動である。横断検索はディレクトリの統合ではなく、Vault MCPが複数のVaultルートを対象にすることで実現する。

ディレクトリは閲覧上の大分類に留め、ノート種別は`second-brain`ではfrontmatterの`type`、`tech-notes`では`tags`で管理する。

`tech-notes`は独立したGitリポジトリであり、ここへはクローンまたはマウントで配置する。`capture-knowledge`、`recall-knowledge`、`deepen-knowledge`、`quiz-knowledge`の各スキルがこのVaultを直接扱うため、ディレクトリ名とカードの書式はスキル側の規約に従い、本書から変更しない。

### 配置しないもの

PDF、映像、OCR全文はVaultへ複製しない。Vaultには、それらから生成した知識と出典参照を保存する。

プロジェクト固有の開発記録、設定値、実装手順は、いずれのVaultにも置かず各リポジトリの`docs/`に残す。Vaultへ入れるのは、そこから一般化した再利用可能な知識と、判断を左右した制約だけとする。

## 命名ルール

ディレクトリ名の区切り文字は両Vaultともハイフンに統一し、空白を含めない。`second-brain`のトップレベルは`{2桁の番号}-{英語Title Case}`、その配下は番号を持たない英語Title Case（複数語もハイフン区切り）とする。`tech-notes`は英小文字のkebab-caseで、スキル側の規約に従う。番号は閲覧順を固定するためのもので、意味を持たせない。

ノートのファイル名は、ディレクトリとは逆に**人間が読む名前**とする。`second-brain`では日本語の見出し名をそのまま使い、ローマ字化や英訳をしない。ディレクトリは機械が扱う器、ファイル名は人間が扱う名前として役割を分ける。

```text
20-Knowledge/Concepts/唯識.md
20-Knowledge/People/世親.md
20-Knowledge/Themes/心の実在性.md
```

原語、英語表記、略称、別表記はファイル名に持ち込まず、frontmatterの`aliases`へ入れる。`aliases`はObsidianの検索とリンク補完の対象になるため、ファイル名を一つに保ったまま複数の呼び名から辿れる。

```yaml
aliases: [vijñapti-mātra, Yogācāra, 唯識派]
```

ファイル名にはOS間で扱いが異なる文字（`/ \ : * ? " < > |`）と、先頭・末尾の空白およびピリオドを使わない。`#` `^` `[` `]` はObsidianのリンク構文と衝突するため同様に避ける。資料由来の題名にこれらが含まれる場合は、ファイル名からは除去し、正式な題名を`title`に保持する。

### 一意性とリンクの形式

`second-brain`ではリンクを**Vaultルートからの絶対パス**で書く。Obsidianの「新規リンクの形式」を絶対パスに設定し、リンクの解決をbasenameに依存させない。

```markdown
[[10-Sources/Papers/上田-2019-唯識の認識論/Sections/01-Introduction|第1章]]
[[20-Knowledge/Concepts/唯識]]
```

これにより、一意性の要求を階層ごとに分けられる。

| 対象 | 一意性の範囲 |
|---|---|
| `20-Knowledge` / `30-Syntheses` / `40-Maps` のノート | Vault全体で一意 |
| 資料ディレクトリ（`Works` / `Papers` / `Academic-Books` 配下） | 各親ディレクトリ内で一意 |
| 章・節・話数ノート | 資料ディレクトリ内で一意 |

`01-Introduction.md`のように文献をまたいで重複する名前は、意図した重複として許容する。絶対パスで参照するため曖昧にならず、ファイル名へ親の情報を重複させる必要もない。

概念・テーマなどVault全体で一意にすべきノートについては、Vault Curatorが作成前に横断で同名を確認する。衝突したときだけ、**後から作る側**に括弧で区別語を付ける。既存ノートは改名しない。改名は既存リンクを一斉に壊し、しかも壊れたことが検出されにくいためである。区別語は`type`または分野名を使う。

```text
20-Knowledge/Concepts/縁起.md          ← 先にあった。そのまま
10-Sources/Works/縁起 (作品)/          ← 後から作る側に付ける
```

表示名を変えたい場合はファイル名ではなく`|`によるエイリアス表記を使い、パスは常に正規のものを書く。パスを変更した場合は、参照元を検索して一括で追随させる。Vault Curatorはノート移動・改名の際、Vault内の絶対パスリンクを走査して更新差分に含める。

`tech-notes`はこの規則の対象外とし、スキル側の規約どおりbasenameの`[[wikilink]]`とVault全体での一意なファイル名を維持する。カードが階層を持たずフラットに近い構造のため、絶対パスにする利点がない。Vault MCPは対象Vaultに応じてリンク形式を切り替える。

## 編集領域の分離

両Vaultとも、AIエージェントが本文を書く領域と、人間が最終判断を持つ領域を分ける。境界をディレクトリとfrontmatterの両方で表現し、Vault Curatorは人間の領域を上書きしない。

### `second-brain`

| 領域 | 編集者 | 扱い |
|---|---|---|
| `10-Sources` / `20-Knowledge` / `30-Syntheses` / `40-Maps` | AI | 生成物の正本。人間は直接編集せず、修正は`00-Inbox`経由で指示する |
| `00-Inbox` | 人間 | 人手確認が必要なノートと、人間の手書きメモの受け口 |
| `90-Meta` | 人間 | taxonomy、テンプレート、運用ルール。AIは読む側に徹し、変更は提案に留める |

`00-Inbox`は双方向の受け口とする。AIは確信度が低い結果や競合をここへ送り、人間はここへ自由に書く。人間が置いたノートをAIが正規の配置へ昇格させるのは、人間が確認した後に限る。

### `tech-notes`

| 領域 | 編集者 | 扱い |
|---|---|---|
| `knowledge/` 本文 | AI | カードの本文はAIが書く。人間の作業は採否と`confidence`の判定に限る |
| `decisions/` | AI・人間 | 判断の記録。制約の形で書き、固有名詞を使わない |
| `confidence: verified` | 人間 | AIは`hearsay`か`reasoned`しか付けない。昇格は人間が手で行う |
| `MOC/` / `templates/` | 人間 | 分類方針の表明。AIは新規分野のMOCを作る以上のことをしない |

`tech-notes`では領域の境界をディレクトリではなく`confidence`が担う。推測が検証済みの顔をして混ざることが最大のリスクであるため、この一点だけは自動化しない。

### 共通の保護規則

- 全ノートのfrontmatterに`owner`（`ai` | `human`）を持たせ、`owner: human`のノートをAIが上書きしない。
- 人間が編集したノートは`status`を`human_verified`とし、再生成の対象から外す。
- 人間が追加したタグ・リンクは、再生成されなかったという理由だけで削除しない。
- 上書きが必要と判断した場合も直接編集せず、差分を検証レポートまたは`00-Inbox`へ出す。

## ノート種別

| 種別 | 用途 |
|---|---|
| `work` | 作品全体の概要、構成、主題、関連資料 |
| `episode` | 話数ごとの要約、批評、作品内での位置づけ |
| `paper` | 論文全体の書誌情報、主張、章一覧 |
| `academic_book` | 専門書全体の書誌情報、主張、章一覧 |
| `chapter` | 章・節ごとの要約、根拠、重要語 |
| `concept` | 「唯識」などの専門用語・概念 |
| `theme` | 複数資料を横断する問い・テーマ |
| `person` | 人物と作品・概念との関係 |
| `comparison` | 複数の作品、定義、理論の比較 |
| `timeline` | 出来事や研究史の時系列整理 |
| `essay` | 出典に基づく統合的な論考 |

## 作品と話数

作品全体と話数を分離し、長編作品でもノートが肥大化しない構成にする。

```text
10-Sources/Works/{作品名}/
├── index.md
└── Episodes/
    ├── S01E01-{話数タイトル}.md
    └── S01E02-{話数タイトル}.md
```

`{作品名}`はMediaVault上の正名をそのまま使い、Vault側で訳や略称を選び直さない。作品メタデータの正本はMediaVaultであり、表記の判断を二重に持つと不一致が常態化するためである。原題、邦題、略称、副題違いは`index.md`の`aliases`へ入れる。ノートとMediaVaultの対応は名前ではなく`item_id`で保つ。

MediaVault側で正名が変更された場合、ディレクトリ名を自動追従させない。改名は既存のリンクを壊すため、差分を検出したうえで確認対象とする。

話数ノートのファイル名は`{番号}-{話数タイトル}`を共通形とし、番号の書式だけを作品形式に応じて切り替える。番号はゼロパディングし、辞書順が原典の順序と一致するようにする。

| 作品形式 | 番号の書式 | 例 |
|---|---|---|
| シーズン構成の映像作品 | `S{2桁}E{2桁}` | `S01E01-銀の懐中時計.md` |
| 通し番号の映像作品 | `E{3桁}` | `E001-旅立ち.md` |
| 巻・話構成の書籍 | `V{2桁}C{3桁}` | `V01C003-決意.md` |

劇場作品や単巻の資料など、内部を分割しないものは`Episodes/`を作らず`index.md`に集約する。分割の有無は資料の構造で決め、分量では決めない。

原典に話数タイトルが存在しない場合は番号だけをファイル名とし、タイトルを補作しない。番号体系がMediaVault側と原典で食い違う場合は、原典の番号を採り、対応を`index.md`に記録する。

話数ノートの一意性は作品ディレクトリ配下で担保する。別作品と話数タイトルが重複してもよい。

話数ノートは、要約、構成、登場人物、主題、批評、作品全体での位置づけ、関連ノート、出典を持つ。要約は原典に明示された内容、批評は解釈として区別する。MediaVault上の話数と原典ファイルを一意に対応づけられない場合は推測で確定せず、確認対象とする。

## 論文・専門書

論文と専門書は資料全体の`index.md`と、章・節単位のノートに分ける。

```text
10-Sources/Papers/{著者}-{年}-{短縮タイトル}/
├── index.md
└── Sections/
    ├── 01-Introduction.md
    └── 02-先行研究.md

10-Sources/Academic-Books/{著者}-{年}-{短縮タイトル}/
├── index.md
└── Chapters/
    ├── 01-識の転変.md
    └── 02-三性説.md
```

ディレクトリ名は`{筆頭著者の姓}-{西暦4桁}-{短縮タイトル}`とする。

- 著者は**筆頭のみ**。共著者はディレクトリ名に含めず、`index.md`の`authors`に全員を順序どおり保持する。著者数でパスの形が変わると、参照する側が名前を組み立てられなくなる。
- 姓は原表記に従う。日本語著者は日本語、欧文著者はラテン文字とし、ローマ字化や訳をしない。
- 西暦は原著の刊行年ではなく、参照している版の年とする。版が複数ある場合は`index.md`に併記する。
- 短縮タイトルは原題の先頭から、その著者・その年の中で資料を識別できる最小限の語まで。目安は日本語で15文字、欧文で3語以内。副題は含めない。
- 同一著者・同一年で衝突した場合は西暦に`a` `b`を付す（`上田-2019a-...`）。

正式な書誌情報はディレクトリ名ではなく`index.md`のfrontmatterが持つ。ディレクトリ名は人間が一覧から見分けるためのラベルであり、書誌の代替ではない。

章・節ノートも`{2桁の連番}-{見出し}`とし、話数ノートと同じ「番号-タイトル」の形に揃える。番号は原典の章番号があればそれを、無ければ出現順の連番を用いる。見出しは原典の表記をそのまま使い、訳や要約に置き換えない。

原典の番号が連番でない場合（`3.1` `付録A`など）は、ピリオドをハイフンに置き換え（`03-1-...`）、番号を持たない部分は`00-`（前付）と`99-`（後付・付録）に寄せる。

章・節ノートの一意性は資料ディレクトリ配下で担保し、参照は絶対パスリンクで行う。

章ノートは、章の目的、要約、主要な主張、根拠・事例、重要語、疑問・反論、出典を持つ。章境界は抽出結果のラベルや目次を優先し、OCR本文から推定した場合は人手確認の対象にする。

## テーマ・専門用語

ThemeとConceptは作品、論文、専門書、Web資料を横断する。

Themeノートでは、問い、対象範囲、資料ごとの定義、共通点と相違点、歴史的文脈、作品例、論争点、暫定的な結論を整理する。Conceptノートでは、定義、原語、別名、系譜、主要概念、学説上の相違、用例、誤解しやすい点を整理する。

## Web資料

Web検索結果は補助資料として扱い、検索結果のスニペットだけを根拠にしない。可能な限り一次資料、査読論文、専門書を優先する。

Web資料には資料単位のノートを作らない。`10-Sources`はMediaVaultが管理する資料に対応する階層であり、Webページはそれに当たらないためである。Webから得た内容は、それを使うConceptノート・Themeノートの本文へ直接書き、根拠は`sources`にURLと取得日で残す。

```yaml
sources:
  - kind: web
    url: https://...
    retrieved: 2026-08-20
    title: ページ題
```

`retrieved`はページ内容が変わり得ることを前提とした必須項目とする。Web出典のみに依拠するノートは`status`を`review_needed`とし、一次資料での裏取りを促す。

## メタデータと出典

全ノートは共通frontmatterを持つ。

```yaml
---
id: kv_01J...
title: 唯識
type: concept
aliases: []
categories: [philosophy]
tags: [buddhism]
status: reviewed
owner: ai
sources:
  - kind: mediavault
    item_id: "..."
    file_id: "..."
    extraction_version: "pdf-v1"
source_refs:
  - source: 0
    chunk_index: 12
    label: p.42-44
provenance:
  workflow: research-topic
  run_id: "..."
  model: "..."
---
```

出典は`item_id`、`file_id`、`extraction_version`、`chunk_index`の組み合わせで追跡する。`label`はページや章を表示するための補助情報とする。再抽出によって`extraction_version`が変わった場合は既存参照を自動的に読み替えず、再確認対象にする。

| `status` | 意味 |
|---|---|
| `draft` | AI生成直後 |
| `review_needed` | 出典不足、推定、競合などがある |
| `reviewed` | 機械的な検証を通過 |
| `human_verified` | 人間が内容を確認済み |
| `stale` | 出典参照が失効している |

## タグ・カテゴリの管理

- `type`: ノートの構造を決める種別
- `categories`: 少数の大分類
- `tags`: 横断検索に使用する特徴語
- Wikilink: 作品、人物、概念など実体間の関係

正規のカテゴリ・タグと表記揺れは`90-Meta`のtaxonomyで管理する。自動管理は候補生成、既存語彙への正規化、差分検証、適用の順で行う。

- 本文と出典に根拠があるタグだけを追加する。
- 未登録語は直ちに正式タグにせず、提案として蓄積する。
- 同義語はaliasへ統合する。
- 人間が追加したタグは既定で保護する。
- タグが再生成されなかったという理由だけでは削除しない。
- タグ削除やtaxonomyの統合は原則として確認対象にする。

MediaVault側のタグ・カテゴリとは別の分類体系として扱い、Vault側の整理結果をMediaVaultへ自動反映しない。
